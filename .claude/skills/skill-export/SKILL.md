# skill-export — 派生リポジトリのスキルを汎用へ輸出する

汎用スキルを配布したリポジトリでは、スキルがそのプロジェクトの事情を吸って育つ。育った結果のうち、どのプロジェクトでも効く部分だけを汎用の置き場へ戻す作業である。

輸出の前提は 3 つある。

- 輸出するのは、プロジェクトが変わっても意味が変わらない部分に限る
- 輸出するものでも、固有の名称・パス・数値は落とすか汎用の語に置き換える
- 派生側のほうが育っているスキルは、派生側を採用する

採否と脱固有化の判定は [CRITERIA.md](CRITERIA.md) に置く。

## 手順

1. 棚卸し
   - `scripts/survey.sh <owner/repo>...` で派生側のスキルを一覧にする
   - 共通・新規・上流管理の別と、固有結合の疑いが出る
2. 読み比べ
   - 共通スキルは差分を行単位で読み、機能追加と固有名称化を仕分ける
   - 新規スキルは本文まで読み、固有部分を抜いても芯が残るかを見る
3. 仕分け
   - 追加候補・更新候補・不採用の 3 つに分ける
4. 合意［人ゲート］
   - 3 つの一覧を報告し、着手前に採否の判断を仰ぐ
   - 判断ポイントは束ねず、1 つずつ細かく尋ねる
5. 取り込み
   - 固有の名称・パス・数値・ドメイン語彙を落として書き込む
   - 文章と構造の作法は、日本語とスキル文書の読みやすさを担うスキルに従う
6. 検証
   - `scripts/verify.sh <落としたはずの語>...` を通す
   - 書き込んだ行を通しで読み、語の検索に掛からない消し残しを拾う
   - 落ちた項目を直してから報告する

## 境界

- 派生側の判断をそのまま正としない
  - 派生側の事情で入った変更は、汎用では誤りになりうる
- 方針そのものを覆す差分を独断で採用しない
  - 人に確認する
- 上流で配布・管理されているスキルを複製しない
- 動作環境の前提を持ち込まない
  - 派生側で動いていることは、輸出先で動くことを意味しない

## 報告のしかた

手順 4 では、追加候補・更新候補・不採用を分けて出す。スキルごとに、何が育ったのか・何を落とすのかを 1 行で添える。不採用は理由まで書く。

判断を要する点は本文に埋め込まず、末尾に分けて挙げる。方針転換・コストの上下・書き換え量が大きいものが該当する。
