# skill-export — 採否と脱固有化の判定

[skill-export](SKILL.md) の手順 2〜3 で使う。個々のスキル・差分をどう扱うかを決める。

## 輸出しないもの

- そのプロジェクトのドメイン知識そのものを持つスキル
- 特定の構成に依存し、固有部分を抜くと芯が残らないスキル
  - 価値が固定値（DB 名・ポート番号・ビルドコマンド・実ファイルへの参照）に集中しているもの
- スキル自身が「このプロジェクト固有」と宣言しているもの
- 上流のリポジトリで配布・管理されているスキル
  - frontmatter の metadata に配布元やタグが入っているものが該当
  - 複製すると二重管理になり、上流の更新から切り離される
  - 内容が汎用でも複製しない。上流を参照する形を勧める
  - 例外は、二つの置き場を意図して併設し、この作業で行き来させると決めている場合
    - この項が防いでいるのは、知らないうちに複製が増えて更新から切り離されることである
    - 併設を選んだ側は切り離しを承知しており、戻す経路も決まっている
    - 使うときは、スキルごとにどちらを正典とするかを決めて記録する。決めないと両方が育って選べなくなる

## 共通スキルの差分の仕分け

派生側の変更には、機能追加と固有名称化が混ざる。まとめて採らず、行単位で分ける。

- 機能追加 — 採る
  - 抜けていた手順の補完、失敗の防ぎ方、判定の精度上げ
- 固有名称化 — 捨てる
  - 汎用の記述を、そのリポジトリのパス・ファイル・ドメイン語へ差し替えただけの差分
  - 例: 「領域別の規約ファイル」という記述を、実ファイルへの直リンクに変えた行
- 前提の付け外し — 内容で見る
  - 特定の設定・ツールの存在を前提にしない書き方へ変わっていれば、汎用では改善にあたる
- 方針転換 — 人に確認する
  - 既存の指示を逆向きにする差分が該当
  - 複数の派生が同じ向きに振れていれば、採るべき兆候として添える

## 複数の派生が別方向に育っているとき

同じスキルに別々の機能が足されていれば、競合しない限り両方を採ってマージする。競合するときは、より汎用な側を採り、もう一方は理由を添えて落とす。

派生どうしで表現だけが違う箇所は、片方を選んで揃える。両方を残して同じことを 2 か所に書かない。

## 脱固有化の型

- 固有名詞 → その語が果たす役割
- リポジトリ内への直リンク → 何を指すかの説明
- 実測値・issue 番号・社内固有の事例 → 考え方だけ残す
- 特定ツール名の前提 → そのツールが担う役割
- 環境依存のコマンド → どこでも動く書き方
  - 特定 OS の拡張に頼る実装は、輸出先の環境が違えば気づかないうちに壊れる
  - 置き換えたら、境界値を含む既知の正解と突き合わせて確かめる
- 例文に紛れた実データ → 例と分かる値
  - 配色の hex・帳票の項目名・画面の固有名は、固有名詞の検索に掛からず例文の中だけに残る
  - 例は、そのプロジェクトを知らない読み手が読んでも意味が変わらない値にする

## 依存の付け替え

派生側のスキルは、輸出先に無いスキルを名指ししていることがある。名指しをそのまま持ち込むと、呼べないスキルへの参照が残る。

- 輸出先にも同じスキルがある → 名指しのまま残す
- 輸出先に無い → その役割を表す語に置き換える
- 輸出したスキルを誰も参照していない → 既存の統合スキルから辿れるようにする
