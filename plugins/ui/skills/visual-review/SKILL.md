# visual-review — 画面の見た目を第三者視点でデザインと突き合わせる

実装した画面が見た目の正本にどれだけ寄れているかを定性的に見る。見た目が一致しているか・どこを直すと近づくかだけを見る。バグ・実装の良し悪し・規約適合は対象外である。アプリを起動してスクリーンショットを撮れる状況で回す。自己確認は構造的に甘くなるため、省略せず第三者を通す。

見た目の正本はデザインツール上のデザインである。以下ではこれを「デザイン」と呼ぶ。どのツールから宣言値と画像を取るかはプロジェクトによる。

## 突合は 2 層で見る

値で照合する層と目で確かめる層を両方通す。片方では足りない。

| 層 | 何を正にするか | 担当する差分 |
|----|----------------|--------------|
| 第 1 層: 宣言値照合 | デザインの宣言値（fill の実 hex・typography・寸法・余白） | 色違い・装飾の有無・バッジの塗り・罫線・寸法。決定的に拾える |
| 第 2 層: 目視レビュー | レンダリングした実物の見え方 | 第 1 層に無い差分（未知の差）・はみ出し・折り返し・実際の整列・フォントの崩れ |

第 1 層を一致の正とし、値で並べて判定する（目視の印象では判定しない）。第 2 層は第 1 層が見られない実レンダリングと未知の差を別担当で拾い、第 1 層の結果を判断材料として受け取る。

## 手順

### 1. 材料をそろえる

両層が使う 3 つを集める。

1. デザインの宣言値を控える
   - 対象要素の fill の実 hex・typography・寸法・余白を取る
   - 色はデザインの実値を写し、自分で色名や hex を発明しない
2. デザインの参照画像を実寸で書き出す
   - 状態（一覧・詳細モーダル・編集モーダル等）ごとに 1 枚ずつ用意する
   - 縮小スクリーンショットで代用しない
   - 実装範囲に切り抜き、範囲外は「別スコープ」と添える
3. 実装のスクリーンショットと token/CSS を控える
   - 全ての状態をレンダリングして撮る
   - 対象要素の token 値・CSS の実値（例 `--color-danger: #b91c1c`）を控える

### 2. 第 1 層 — 全宣言値を総当たりで照合する

[CHECKLIST.md](CHECKLIST.md) の各行を上から機械的に全行潰す。指摘された項目だけ拾うのではない。要素ごとに「デザインの宣言値」と「実装の token/CSS の実値」を並べて値で判定し、見ていない要素を残さない。事前に渡された差分リストがあっても列挙の代わりにせず、最後の答え合わせにだけ使う。

```text
必須バッジ fill: デザイン #2F80ED vs impl .req → --color-danger #b91c1c … 不一致（要修正）
タイトル帯 背景: デザイン #123456 vs impl .head 背景なし(白) … 不一致（要修正）
ラベルの「：」: デザイン 各行に ： テキスト有り（ラベル列 固定幅で整列） vs impl ： 無し … 不一致（要修正）
```

一致は「同じ色か」「同じ有無か」で判定する。形式が違っても同じ色なら一致とする（`#b91c1c` ＝ `rgb(185, 28, 28)`）。「だいたい近い色」は一致にしない。不一致は既定で「直すべき差」とし、手順 4 へ送る。

### 3. 第 2 層 — 第三者に見させる

Agent ツールで別コンテキストのサブエージェントを起動する。画像どうしの突き合わせ＝視覚処理が主タスクなので、`model: opus` を明示して常に最新の Opus 系を使う。実装意図・弁護や具体的な直し方（色名・数値）は渡さず、状態ごとに実施する。第 1 層の差分リストを判断材料として渡し、「全差分をブラインドで探す」でなく「値照合済みを踏まえ未知の差とレンダリング実物を確認する」に振る。

プロンプトに必ず含める:

> あなたは実装会話を持たない第三者のレビュアーです。1 枚目が実装、2 枚目が設計（見た目の正本）です。あわせて、すでに値で照合した差分リストを渡します。これを踏まえ、(1) リストに**載っていない**差分（未知の差）、(2) レンダリングした実物がデザインと一致しているか（はみ出し・折り返し・実際の整列・フォントの崩れ・見切れ）を中心に挙げてください。アイコンや記号（✓ ＋ × 矢印・検索など）は文字に書き起こさず、図形として見てください。片方がアイコン・もう片方が文字、のような取り違えは差分として挙げてください。各指摘は必ず **どこの・どの要素か** を特定してください（どのセクション／モーダルの、どのボタンや項目か。画面内の位置も添える）。ずれの大きさは向きと程度を言葉で伝えてください。ピクセル値の計測は不要です。各指摘に、それが「直すべき差」か「意図的な差」かの見立てを添えてください。バグや実装の良し悪しは見ません。見た目だけを評価します。各指摘は要点を絞り、簡潔に書いてください。

### 4. 仕分けして反復する

第 1 層・第 2 層の指摘を等しく仕分けする。残差がすべて次のいずれかになるまで手順 2〜3 を反復する。

- 既定は「直すべき差」
  - 直して再撮影・再照合する
- 「意図的な差」は理由の記録が必要
  - PR 本文に「意図的な差」セクションを設け、差分ごとに 1 行（対象要素 / 差分内容 / 理由）で書く
  - 理由はデータ境界・スコープ外の明示に限る
  - 同じ理由が複数の差分にかかるときだけ、対象要素を列挙して 1 行に束ねてよい
- 密度・フレーム範囲の差は要件オーナーの確認へ回す
  - font サイズ全体やページ枠寸法など、実装システムの方針と衝突しうる差は勝手に直さない
  - 第 1 層では差として記録し、潰さない

「意図的な差」の書き方の例を示す。

```text
## 意図的な差
- 連絡先の追加ボタン: デザインは青アイコンのみ / 実装は白ボタン「＋追加」 … 別 feature 所有のモック。所有 feature の実装時に寄せる
- 住所・電話番号の入力欄: デザインの塗りに寄せるが値は保存されない … いずれも別テーブル所有（同一理由で束ね）
```
