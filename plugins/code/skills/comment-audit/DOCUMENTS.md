# 文書の棚卸し

comment-audit の判断基準を文書へ広げたものである。残すもの・削るものの軸は SKILL.md にあり、ここは文書に固有の扱いだけを置く。

コメントより深刻になりやすい。コメントは実装のすぐ隣にあるので嘘に気づけるが、文書は物理的に離れており、差分レビューにも乗らない。

## 寿命で分ける

- 記録
  - 設計判断、却下した案、その時点の前提
  - 更新せず、日付を明記して残す
  - 決定が変わったら記録を足し、古いほうに「置き換え済み」と書く
  - ADR やその運用を制度化したものが該当する
- 常時更新
  - README、アーキテクチャ概要
  - 陳腐化するので薄く保つ

この二つが混ざった文書は、分離を提案する。

## 転記しすぎない

コードを読めば生成・確認できる情報は転記しない。テーブル定義、API エンドポイントの一覧、ディレクトリ構成図などは、生成に寄せるか、参照先を示すだけにする。

## 文書にこそ書くもの

コードには表せない。積極的に残す。

- 何を作らないか
- 却下した設計案とその理由
- ファイルをまたぐ全体構造と責務の分担
- 非機能要件の根拠
  - なぜこの規模を想定したか
- 運用時の判断材料
  - 障害時にどこを見るか

## AI へ渡す前提知識は別に扱う

CLAUDE.md や要約文書のように AI へ渡す前提知識は、人間向けとは最適な点が違う。人間なら暗黙に共有している事柄も、このプロジェクトではこうする、と明示する価値がある。多少冗長でも構わない。
