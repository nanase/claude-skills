# comment-audit — コメントを棚卸しする

コメントを機械的に減らす作業ではない。コメントが持つ信号を回復する作業である。

コメントがまばらなうちは、コメントがあること自体が「ここは自明ではない」という警告として働く。全行に均等な注釈が付くと、本当に注意すべき箇所を見分けられなくなる。生成されたコードはこの状態へ倒れやすい。総量が変わらなくても、コードの見通しが悪くなり、読み込み時のコンテキストを圧迫し、実装とコメントの二重管理が始まる。

文書を対象とするときの判断は [DOCUMENTS.md](DOCUMENTS.md) にある。

## 残すもの

コードから復元できない情報だけを残す。

- なぜこの実装なのか
  - 特に、検討して却下した選択肢があるとき
- 外部の事情
  - 仕様書の該当箇所
  - ライブラリの既知の不具合への回避策
  - ハードウェアやプロトコルの制約
  - 業務ルールの根拠
- その場を読むだけでは分からない前提
  - 呼び出し順序の制約
  - 暗黙のロック
  - 呼び出し側が保証している事項
- 不具合に見えるが意図的な箇所
  - 将来の誰かに「修正」される危険がある

公開 API や関数境界のドキュメントコメントは別に扱う。実装の言い換えではなく契約なので、実装を変えても嘘にならない。

## 削るもの

- 処理内容の言い換え
  - `// ユーザーを取得する` の類
- 関数名・型シグネチャの再掲
- 変更内容の説明
  - `// エラーハンドリングを追加` の類
  - コミットメッセージの領分で、数か月後には文脈を失う
- 各行への機械的な注釈
- 区切り線・装飾だけのコメント

## 迷ったとき

### 陳腐化の速さで測る

「なぜ」と外部の事実は陳腐化が遅い。「何をしているか」は実装を変えるたびに嘘になる。保守の負担は主に後者で膨らむので、判断に迷ったらこの軸で選ぶ。

### コメント以外の手を探す

コメントを書きたくなる箇所は、命名の変更や関数の抽出で解けることが多い。削除候補を挙げるときは、この代替案も併せて出す。

## 手順

1. 範囲を確認する
   - 対象のファイル・ディレクトリの指定が無ければ聞く
   - 範囲が広いなら、まず 1 ファイルで方針をすり合わせてから広げる
2. 分類する
3. 報告する［人ゲート］
4. 承認されたものだけ直す
   - ついでの整形や無関係な変更を混ぜない

### 分類

| 分類 | 内容 |
| --- | --- |
| 保持 | コードから復元できない情報 |
| 削除候補 | コードの言い換え、名前の再掲、変更履歴 |
| 要確認 | 実装と食い違っている、またはその疑いがあるもの |

### 報告

コードは変更せず、報告だけを行う。削除は人の承認を待つ。判断ミスに気づく機会を残すため、この分離は外せない。

要確認を先に、具体的に示す。実装とコメントの食い違いを洗い出すのが、この作業で最も価値のある部分である。人は目視で見落としやすく、古いコメントは AI をより強く誤らせる。

要確認のものは勝手に直さない。コメントが古いのか実装が壊れているのかは、外から判断できないことが多い。

形式は次のとおり。

```text
## 要確認（実装との食い違い）

- `path/to/file.go:42`
  コメント: 「タイムアウトは 30 秒」
  実装: 10 秒 (`timeout = 10 * time.Second`)
  → どちらが正しいか判断が必要

## 削除候補

- `path/to/file.go:15` — 関数名の言い換え
- `path/to/file.go:88` — 変更履歴。コミットメッセージへ
  （件数が多いなら種類ごとにまとめる）

## 命名・構造で解けるもの

- `path/to/file.go:60` — `// 有効期限切れを除外` は
  `filterExpired()` への抽出で不要になる

## 保持

- `path/to/file.go:120` — ライブラリの不具合の回避策。理由が書かれていて有用
```

## 実装を変更するとき

この作法は棚卸しのときだけのものではない。既存コードを編集したら、その周辺のコメント・文書が古くなっていないかを確認する。古いものは削除するか直す。放置しない。
