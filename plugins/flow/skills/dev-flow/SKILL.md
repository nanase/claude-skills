# dev-flow — feature 開発フローのオーケストレータ

機能開発を受けてから PR がマージ可能になるまで、各スキルを順に呼んで自走させる。2 層アーキテクチャの上層で、自身は実作業をしない。呼ぶ順・分岐点・停止位置だけを持ち、各スキルの中身は再説明しない。

不可逆な操作・課金・法令/安全/承認・権限・要件の曖昧さに関わる判断は、実行前に止めて確認する。迷えば止める（[ESCALATION.md](ESCALATION.md)）。

## 到達点で止まる位置を決める

要件・設計の合意とは別の軸である。未指定なら着手前に確認する。選んだ到達点で主軸を止め、その先の手順へ進まない。

- 検討のみ → 設計提案（主軸 5）まで
  - 実装（6）以降へ進まない
- コミットまで → 実装・テスト・自己レビューの後にコミットして停止
  - 提出（9）の push・PR とマージ可能まで（10）へ進まない
- マージ可能まで → 主軸 10 まで通す
- 質問できない `/loop`・スケジュール文脈では、最も巻き戻しやすい「コミットまで」（push しない）で止める

## 主軸（feature モード）

1. 着手前チェック
   - `git status` → クリーンなら main を最新化 → `feature/<topic>` ブランチ（非 ASCII 禁止）を切る
     - worktree で作業するときは、先にブランチを切らず、`EnterWorktree` の直後に `git branch -m` でこの名前へ付け替える。`EnterWorktree` は `worktree-` を前に付けた名前でブランチを作るため
   - クリーンでない/要件が曖昧なら止めて確認
2. 要件確定［人ゲート］
   - 作る範囲が曖昧なときだけ `requirements-define`
   - 固まっていれば飛ばす
3. 周辺探索
   - 触る対象の周りを薄く見る
   - 範囲は不可逆性に比例（DB スキーマ・共有部品・公開 API は広く、末端のロジックは最小）
4. 設計
   - 既存実装に倣う
   - UI を含むならデザイン確定の流れ（参照デザイン → HTML/CSS 確定 → 実装後に `visual-review`）を通す
5. 設計提案［人ゲート］
   - 後戻りしにくい選択肢があるときだけ `design-proposal`
   - 一意なら飛ばす
6. 実装
   - 既存実装に倣う
   - UI は確定 HTML/CSS を対象フレームワークへ移す
   - TDD（Red→Green→Refactor）
7. テスト・lint・build
   - 生成物を持つ定義（スキーマ・IDL など）を変えたら、テスト・lint の前に生成し直し、生成物の差分をコミットに含める
   - プロジェクトのコマンドを成功させる
   - UI 変更を伴うときはアプリを起動して実際に操作して確かめる
     - 変更操作を実行するだけでなく、その結果が他画面・親コンポーネントへ反映されるかまで見る
     - 一覧画面のフィルタ・件数・関連列など、変更操作を行った画面以外に波及する表示を見落としやすい
   - 決定的コマンドはスキルにしない
8. 自己レビュー［常設ゲート］
   - push 前は軽く保ち、独立した観点別レビューは PR 時（レビュー bot の自動増分と `pr-review-loop`）へ寄せる
   - 差分の重さで 3 段に分け、迷えば軽い段へ倒す
   - 軽微（ドキュメント・整形・設計に影響しない定常的な依存の更新）は飛ばす
   - 通常（新規機能の初回実装を含む大半の差分）は実装コンテキストのまま 1 パス自己点検し、設計・規約に効く差分なら `convention-review` を足す
   - 高リスク（本番データ・承認ルート・権限・法令で定めのある処理に触れる差分）と明示依頼のときは、加えて別コンテキストで `/code-review`（正確性バグ・簡素化）
   - `/code-review` の effort は自動発動なら medium を上限とし、深く見たいときだけ明示依頼で上げる
9. 提出
   - commit→push→PR
   - PR は draft で起票する。レビュー bot は draft を見ないので、CI を直す push でレビュー回数を消費しない
   - 分類ラベルを付ける
   - Issue なしタスクは `feature/` 経路で代替し、受け入れ条件を PR 本文に明記
10. マージ可能まで
    - CI が落ちたら draft のまま直す
      - draft 中の push はレビュー回数を消費しないので、ここで何度直してもよい
    - CI がグリーンになり PR 本文が確定してから Ready にする
      - Ready 化がレビュー bot の第 1 巡であり、レビュアーへの通知でもある
      - Ready にできるのは自分の PR のうち 1 本だけである。`gh pr list --author @me --state open --json number,title,isDraft` で他に Ready の PR が無いか確かめる
        - 無ければそのまま Ready にする
        - 有ればどちらを先に通すかをユーザーへ確認する
        - 委譲を受けて動いているときは、ユーザーではなく委譲元の許可に従う
    - Ready 化の後に `/loop` で `pr-review-loop` を回す
    - CI 失敗対応と、指摘の規約への反映を含む
    - マージ可能と判定する直前に、最後に CI が成功した時点より main が進んでいないか確かめる
      - 進んでいなければ、回し直さずにマージ可能と判定する
      - 進んでいたら、空コミットの push で CI を再実行し、グリーンを確認してから改めて判定する
        - 目的は、PR の内容と最新の main を合成した状態へ CI を当てることである。空コミットの push はマージベースを動かさずにこの目的を満たす
        - Re-run と手動実行では最新の main を取り込めない。Re-run はやり直し前と同じマージ結果を、手動実行は PR のブランチ単体を検証する
        - main を PR ブランチへ取り込むマージでも同じ目的は果たせるが、マージベースが動いて PR の差分表示が変わるため既定にはしない。行うときは PR にその旨を明記する
      - 回し直さない例外は、main 側の変更がすべて CI の結果に効かないドキュメントだけのときに限る
        - 「PR のファイルと重ならない変更」に広げない。ファイルが重ならなくても、main 側の定義の変更が PR 側のテストを壊すことがある
      - `pr-review-loop` の完了判定（HEAD の SHA を突き合わせる規律）と同じ性質の規律で、ベースが古い PR が緑のままマージされる経路を塞ぐ

予定した人ゲートは自動で正否を判定できない 2 段（要件・設計）に限る。ただし [ESCALATION.md](ESCALATION.md) の STOP 条件は全段階で適用し、該当すれば実装中でも止めて確認する。

## 分岐点 — 横断インフラは先行 PR へ

複数の画面・機能が再利用する土台（共通スタイル層・トークン・テスト基盤・サービス層ヘルパ等）が混ざるときは、要件 PR に同梱せず先行の独立 PR に切り出す。土台が無ければ分割しない。提出（主軸 9）の前に見極める。

## 分岐点 — PR 粒度は束ねて CI 実行数を抑える

PR の起票と追加コミットの push は、それぞれ CI 実行を 1 回消費する。独立して検証・リリースできる単位を保ったまま、複数タスクを束ねて 1 PR にまとめられないか、提出（主軸 9）の前に見極める。

- 前節で切り出した先行 PR は束ねの対象外とする
  - 独立した検証・リリース単位として扱う
- push 前にローカルでテスト・lint・build を通す規律（主軸 7）は、追加コミットによる push 回数の削減にもなる

## 分岐点 — stacked PR は base を付け替えるまで CI が走らないことがある

CI のトリガーを base が `main` の PR に限っているなら、PR を積み重ねる（base を前段 PR のブランチにする）と、前段がマージされて base を `main` へ付け替えるまで CI が一切実行されない。base の付け替え自体も CI を起動しない。GitHub Actions の `pull_request` の既定アクティビティタイプは `opened`/`synchronize`/`reopened` で、base の変更（`edited`）は対象外である。付け替えた後は、push で `synchronize` を起こすか手動実行して、初めて CI が走る。積む段取りは、前段のマージ→ base 付け替え→ push または手動実行→ここで CI 検証、という順を前提に組む。

## 分岐点 — サブエージェントのモデルは作業の種類で選ぶ

渡す作業が読み取りだけか、書き込みや判断を伴うかで、モデルの系統を分ける。モデルは版名でなく系統名（Haiku 系・Sonnet 系・Opus 系）で指定する。

- Haiku 系は、ファイルの大量読み取り・件数の集計・一覧化に限る
  - 求める報告は、事実の列挙（file:line・件数・抜粋）にとどめる
  - 採否・優先度・削除可否などの判定は求めない
  - 報告のうち提案や変更に使う項目は、メインが自分で grep・Read して裏を取る
  - Explore は、読み取りの指示でもリダイレクトで一時ファイルを作ることがある。終わったら `git status` などで残骸を確かめる
- 書き込み（Edit / Write など）や判断を伴う作業は、Sonnet 系以上にする
- スキルが `model:` を明示しているときは、そのスキルに従う（`convention-review`・`visual-review`）

## bug モード

不具合起点は主軸の前段に `reproduce-diagnose` を差し、後半（設計〜マージ可能）を feature の主軸と共有する。重複実装しない。

1. 着手前チェック — feature の主軸と同じ
2. 再現と原因の特定
   - `reproduce-diagnose` で再現手順・原因の所在（file/line）・直す/直さないの判断材料・修正方針候補を得る
   - これが周辺探索（3）と設計（4）の入力を兼ねる
   - 再現できなければ止めて確認
3. 判断材料を人ゲートへ渡す
   - 直す/直さないの確定は要件確定ゲートへ渡す
     - 直さないと決まればそこで止める
   - 修正方針の承認は設計提案ゲートへ渡す
     - 修正方針候補をそのまま選択肢にする
4. 以降は feature の主軸と同じ
   - 実装 → テスト・lint・build → 自己レビュー → 提出 → `pr-review-loop`

本番データ・承認ルート・権限に触れる再現/修正は、実行前に止めて確認する（再現と原因の特定を担うスキルの安全の節と [ESCALATION.md](ESCALATION.md) に従う）。人ゲートは要件・設計の 2 段のまま増やさない。
