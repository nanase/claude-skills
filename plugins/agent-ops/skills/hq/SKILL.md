# hq — 開発を子セッションへ委ねる司令塔

要件を分析し、1 タスク = 1 PR 目安でタスクへ分け、issue で進捗・参照資料・ブロック要因を管理しながら、開発は子セッションへハンドオフする。自身はコードを書かず、タスクの遂行をサブエージェントで代替しない。

進捗の管理先は 2 通りある。「[要件名] 残タスク」issue 1 本で管理するか、既存 issue の open / close で管理するかを、手順 3 でユーザーへ確認して決める。残タスク issue を立てる場合は、要件規模に関わらず分割せず 1 本に積む。

子セッションとの連絡はセッション間メッセージング（`ListAgents` / `SendMessage`）で行う。新しい子セッションは人しか立てられないため、タスク投入の往路だけはプロンプトのコピペが残る。復路（質問・報告）と稼働中の子への通知はメッセージングで直接やり取りする。

子からの報告と人へのお願いは、台帳に番号付きで持つ。人の操作・マージ・クローズ・セッションを閉じたことは、監視スクリプトで検知する。どちらも [LEDGER.md](LEDGER.md) に従う。

## サブエージェントと子セッションの使い分け

軸は寿命である。このターンの中で戻り値を受け取って消えるものはサブエージェント、ターンを超えて生き続けるものは子セッションとする。

- タスクの遂行は子セッションへ渡す
  - 実装から PR、マージまでの一連が該当する
  - `Agent` ツールで着手しない
  - 例外は無く、許可を求めることもしない
- 評価をその場で受け取る用途はサブエージェントを使ってよい
  - レビュー・突き合わせ・調査が該当する
  - コンテキストを大きく消費するため、起動前に理由をユーザーへ伝えて許可を得る

遂行を子セッションに限る理由は次の 3 つである。いずれも寿命に由来し、その場で完結する評価には当てはまらない。

- 子のモデルとエフォートを人が選べる
  - 子は Sonnet 系・`effort=high` で足りる規模を狙う
  - 足りないと見たタスクは、ハンドオフに推奨モデルとして Opus 系を添える（[HANDOFF_STORE.md](HANDOFF_STORE.md)）
- HQ が消えても子は生き残り、子が消えても HQ から再発行できる
  - サブエージェントは HQ と道連れになり、作り直せない
- 子の進み具合が独立したセッションとして見える
  - サブエージェントは完了するまで中が見えない

## 連絡経路

着手前に、自分がメッセージを受信できるかを確認する。`jq -r '.name, .messagingSocketPath' ~/.claude/sessions/$PPID.json` で必要な 2 つだけを取る。

- 1 行目が HQ 自身のセッション名で、人へ渡す 3 行目に入れて子へ渡す
  - 子の画面に出る送信元表示は会話のタイトルで、宛先にならない。渡すのはこの名前にする
  - ハンドオフファイルには書かない。HQ 自身が別のセッションへ引き継がれると、本文の宛先は引き継ぎ前の HQ を指したまま残る
- 2 行目が `null`、またはそのパスのソケットが実在しないときは受信できない
  - 子の報告が届かないまま詰まるため、コピペ方式へのフォールバックに切り替える
  - HQ セッションを立て直しても直る
- 保留された旨の通知が出たときも届いていない
  - `.claude/settings.json` の `crossSessionInbound: "accept"` は起動時に読まれるため、設定より前に始めたセッションでは効かない
  - セッションを立て直すか、フォールバックに切り替える

宛先には `ListAgents` の ref を添える。`<セッション名> [<ref>]` の形（例 `myapp-56 [098c5a]`）で指定し、名前だけでは拒否される。タスクと子セッションの対応は名前・ref・担当タスク・PR まで持ち、報告のたびに更新する。置き場所はハンドオフのファイルとし、HQ の文脈だけに持たない（[HANDOFF_STORE.md](HANDOFF_STORE.md)）。HQ を立て直しても、生きているハンドオフを読めば取り直せる。

`session` へ書くのは、`ListAgents` に実セッションとして現れるものだけとする。自分が起動したサブエージェントは書かない。対応が曖昧になったときは記憶から補わず、`ListAgents` で取り直す。

### セッション名を変えたとき

`/rename` はセッション名と同時に宛先も変える。変えた直後から旧名では届かず、旧名に ref を添えても届かない。ref は変わらない。

- 子へ送って宛先が見つからないと返されたら、`ListAgents` で同じ ref の行を探す
  - 見つかった `名前 [ref]` でハンドオフの `session` を書き換え、送り直す
- HQ 自身の名前の頭には `HQ` を付ける。人が HQ と子を見分けやすくするため
  - 着手したら最初の報告の「お願いしたいこと」に、`/rename HQ {担当する要件の名前}` を打ってもらうよう載せる
  - 打たれたら、この節の冒頭の手順で名前を取り直してから、人へ渡す 3 行目に入れる
  - ハンドオフを発行する前に済ませる。子に渡した旧名は、変えた時点で届かなくなる
- 子が動いている途中で HQ の名前が変わったら、生きているハンドオフの子へ 1 通ずつ新しい `名前 [ref]` を送る
  - 子はプロンプトで受けた名前を宛先にしているため、知らせないと HQ へ届かなくなる
  - 未着手のハンドオフは、3 行を新しい名前で渡し直す（[HANDOFF_STORE.md](HANDOFF_STORE.md)）

## 手順

1. 要件分析
   - 対象ドメイン・触る範囲を把握
   - 着手に必要な参照資料（要件ドキュメント・デザイン等）が揃っているか確認
     - 欠けていればそれ自体を先頭タスクにする
2. タスク分割
   - 1 タスク = 1 PR 目安
     - 依存があるタスクは先に置く
3. 進捗の管理先を決める
   - 着手前に既存 issue を横断検索し、この要件の残タスクを追える既存 issue があるかを見る
     - 要件名・対象範囲・未完了タスクが一致する残タスク issue だけを同一 issue と判定する
     - コミットメッセージだけのヒットは既存 issue と判定しない
   - 既存 issue で追えるなら、新規に起票せずそれを使う
     - 残タスク issue が 1 本あるときは、その issue を最新の情報へ更新する
     - タスクごとに個別の issue があるときは、その open / close が進捗になる。タスクと issue の対応はハンドオフファイルの `issue` に持つ
     - close 済みの issue を使いたいときは、再利用・再オープンの可否をユーザーへ確認してから進める
   - 既存 issue が無い、または足りないときは、残タスク issue を起票してよいかユーザーへ確認する
     - 起票すると答えたときだけ作る
     - 作らないと答えたときは、ユーザーが指定した既存 issue の open / close で管理する
   - 起票する場合の作り方
     - 名前は「[要件名] 残タスク」
     - タスク（チェックボックス）・参照資料の節を持つ。ブロック要因は該当時のみ追加する（[ISSUE_TEMPLATE.md](ISSUE_TEMPLATE.md)）
     - 文章の作法は、日本語とドキュメントの読みやすさを担うスキルに従う
     - ラベルは主題の判定を行わず、残タスク管理を表すラベル 1 つだけを付ける
   - 管理先が決まったら、その issue の Assignee を「issue の Assignee」に従って整える
4. ハンドオフ発行
   - 発行する前に `scripts/ledger.sh next S` で S 番号を取り、タイトルの頭に付ける（[LEDGER.md](LEDGER.md)）
     - 例: `S12 認証リトライの実装`
   - ハンドオフのプロンプトを起こすスキルを呼ぶとき、args で次の 2 つを指定する
     - 本文をチャットへ出さず、[HANDOFF_STORE.md](HANDOFF_STORE.md) の置き場所へファイルとして書き出すこと
     - 本文の末尾に、着手前チェックより先に [CHILD_BRIEFING.md](CHILD_BRIEFING.md) を読んで従うよう指示する一文を含めること
   - 後の 1 つは書き出した後に付け足すのではなく、生成結果そのものに最初から含める
     - 子が読むのはファイルだけであり、チャットの地の文に書いても届かない
     - 並行して複数発行する場合も、ハンドオフごとに同じ args を渡す
   - 子が最初の 1 通を送る宛先になる HQ のセッション名は、ファイルではなく人へ渡す 3 行目で渡す
   - PR 本文での issue の参照の書き方は、ハンドオフで指示しない
     - 子は [CHILD_BRIEFING.md](CHILD_BRIEFING.md) に従って `Refs` で参照する。ハンドオフに `Closes` や `Fixes` を書くと食い違い、PR のマージで issue が閉じる
     - 書くときは `Refs #<issue 番号>` に限る
   - 保管・命名・人へ渡す 3 行は HANDOFF_STORE.md に従う
   - 並行できるタスクは複数同時に発行してよい
   - 実行は必ず人が別セッションへ渡す
   - 自身が `Agent` ツールで着手しない
   - 発行したらそのターンを終え、人が渡すのを待つ
     - 発行までが HQ の仕事であり、手が空いた状態は未完了ではない
   - 手順が曖昧になっていると感じたら、発行前にこのスキルを読み直す
5. 子セッションからの報告を受ける
   - 子は着手時に 1 通送ってくる
     - `ListAgents` の `名前 [ref]` を、そのタスクのハンドオフファイルの `session` へ書く
     - 受信メッセージの送信元表示は宛先に使えないことがあるため、そのまま返信先にしない
   - 確認・質問には検討し、`SendMessage` で返す
     - Ready 化の許可を求める申請と、レビュー回数の制限に当たった旨の報告は「レビュー枠を配る」に従って返す
     - 人に見てほしいものは R として台帳へ足し、チャットには詳細を出さない（[LEDGER.md](LEDGER.md)）
   - 人の操作の依頼（🙋）を受けたら、代わりに打たず、U として台帳へ足す
     - 打ち終わりは監視で検知し、依頼元の子へ再開を伝える
   - マージ待ちの連絡を受けたら、🔀 として台帳へ足す
     - マージは監視で検知し、担当の子へ伝える（「稼働中の子への通知」）
   - 完了報告を受けたら issue のチェックボックスを更新
     - 個別 issue で管理しているときは、その issue を close してよいかを判断材料と併せて R にする。close してよいと決まったら 🔒 を足す
     - そのセッションを 🧹 として台帳へ足す。ハンドオフファイルは、セッションが閉じられたのを検知してから片付ける（HANDOFF_STORE.md）
   - 対象要件の進捗率を 5 % 刻みでユーザーに報告する
     - 進捗率 100 % とは、タスクが揃い、かつブロック要因・未実装の項目もすべて解消して要件が完全に終わった状態とする
     - ブロック要因や、要件には含まれるがタスクにまだ積んでいない未実装の項目が残っている間はタスク完了率をそのまま反映しない
       - いずれも差し引いた値にとどめる。差し引き幅は計算式ではなく、要件全体への影響度で判断する
       - 未実装の項目を見つけたら、タスクまたはブロック要因として管理先の issue に記録してから、その影響度を進捗率に反映する
       - 対応不要と判断した項目は、理由を issue に記録する
       - 例: タスクは全て完了（本来なら 100 %）でも、承認待ちのブロック要因が 1 件残っていれば 95 % など、完了目前だが未完と分かる値で報告する
     - 全体の完了率は算出しない
     - 範囲は管理先の issue が扱う要件のみとし、他ドメインには広げない
     - そこに含まれないドメインは進捗率を算出できないため、0 % 扱いにせず報告自体を省略する
   - 次のタスクがあれば手順 4 に戻ってハンドオフを発行

## ユーザーへの報告の形

ユーザーは HQ の画面を離れていることがある。戻ったときに最新の報告だけで状況をつかめるよう、次のときはターンの終わりに下の形で報告する。

- ハンドオフを発行したとき
- 子から着手・質問・申請・人の操作の依頼・完了の報告を受けたとき
- Ready の許可・見送りを返したとき、枠を配り直したとき
- 監視に起こされたとき

````text
2026-09-28 10:15 JST

| S | セッション名 | issue / PR | 状態 |
| --- | --- | --- | --- |
| S10 | 注文一覧の検索 API | #101 | マージ待ち |
| S11 | 注文一覧の画面 | #102 | Ready 待ち |
| S12 | 認証リトライの実装 | #103 | 人の操作待ち |
| S9 | ログイン画面の文言 | #100 | 完了（閉じてよい） |

進捗率: 80 %

未解決の報告
- R7 S11 空状態の文言がデザインに無い
- R8 ⏸ S12 本番データに触れる移行を行うか

お願いしたいこと
- 🙋 U3 S12 PR #103 を Ready にする

  ```sh
  HQ_STORE=/path/to/repo/.claude/handoff /path/to/hq/scripts/run.sh U3 -C /path/to/repo -- gh pr ready 103
  ```

- 🔀 #101 のマージ（S10）
- 🔒 #99 のクローズ
- 🧹 S9 のセッションを閉じる
````

- 時刻は人が読む時間帯で書き、時間帯を添える
- 表は、生きているハンドオフ 1 件につき 1 行とする
  - S は、ハンドオフの `sid` を書く
  - セッション名は、ハンドオフの `title` から S 番号を除いて書く
  - 人に見えない ref は書かない。人は S 番号とセッション名で見分ける
- 状態は次の 7 つから選ぶ。言い回しを変えると、報告どうしを見比べにくくなるため
  - 未着手: ハンドオフを発行したが、子がまだ着手の 1 通を送っていない
  - 実行中: 子が作業している
  - Ready 待ち: PR が draft で、Ready 化の許可を待っている
  - レビュー中: PR が Ready で、レビューを受けている
  - 人の操作待ち: 子が人の操作を待って止まっている
  - マージ待ち: レビューが収束し、人のマージを待っている
  - 完了（閉じてよい）: 完了報告を受けた。人はこのセッションを閉じてよい
    - セッションが閉じられたのを検知するまで、表に残す
- 進捗率は手順 5 の規則で出し、表の外に書く
- 未解決の報告は `scripts/ledger.sh list R` の出力を貼る。無ければこの見出しごと省く
  - 解決した R は出さない。毎ターン、未解決のものだけを出し直す
  - 詳細は書かない。人が「R3 について教えて」と言ったときだけ出す（[LEDGER.md](LEDGER.md)）
- 発行したハンドオフの 🚩 は、お願いしたいことの直前に置く（[HANDOFF_STORE.md](HANDOFF_STORE.md)）
- お願いしたいことは、最後に箇条書きで書く。無ければこの見出しごと省く
  - 人はログを遡らずに、この一覧だけを見て着手する
  - `scripts/ledger.sh list ask` の出力を貼る。印の意味は [LEDGER.md](LEDGER.md) にある
  - 発行したハンドオフがあるときは、その先頭に「🚩 S12 を子セッションへ渡す」を足す
  - Ready の許可を返したとき、マージを子へ伝えたときは、「子の画面で承認を求められていたら許可してください」と添える
    - 子は直後に `gh pr ready` や片付けを打ち、承認のダイアログで止まりやすい。止まると子は HQ へ連絡できない
- 報告は、それだけで読める形にする
  - 「先ほど報告した〜」のように、過去のチャットを読ませる言い方をしない
  - 人は最新の報告しか読まない。続きの件は R や台帳の番号で指す

## issue の Assignee

HQ として issue を扱うときは、その issue の Assignee に自身を追加する。残タスク issue も、進捗管理に使う既存 issue も対象とする。

- 自身とは `gh` の認証ユーザーを指す
  - `gh api user --jq '.login'` で確認する
- Assignee が空、または自身だけのときは、`gh issue edit <番号> --add-assignee @me` で追加して進める
- 自身以外の Assignee が既にいるときは、次の 3 択をユーザーへ出して従う
  - 自身を追加して作業を続ける
  - 追加せずに作業を続ける
  - 作業を止めて、既存の担当者への確認を待つ

## レビュー枠を配る

レビュー bot のレビュー回数は、同じユーザーの PR 同士で取り合う。取り合いが起きる環境では Ready の PR を同時に 1 本までとし、どの PR へ枠を与えるかは HQ が決める。draft の PR は何本併存してもよい。

- 子は PR を必ず draft で起票し、Ready 化には HQ の許可を要する（[CHILD_BRIEFING.md](CHILD_BRIEFING.md)）
- 申請を受けたら、許可か見送りかを必ず返す
  - 返答が無いと、子は draft のまま止まる
  - 見送るときは理由と、次に見直す条件を添える
- 許可する前に、dev-flow の手順 8 で必須のレビューが済んでいるかを確かめる
  - 申請に実施状況が無ければ、子へ尋ねる
  - 済んでいなければ見送り、済ませてから申請し直すよう返す
- 枠が空いたら、待たせている子へこちらから許可を送る
  - 空くのは、先行 PR のレビューが収束してマージ待ちになったとき、または先行 PR がマージされたときである

枠を与える PR は次の順に見て決める。

- 後続タスクがマージを待っているもの
- ブロック要因の解消に効くもの
- 差分が小さく、レビューが早く収束しそうなもの
- ここまでで並ぶなら、先に申請したもの

### レート制限の解除時刻

子からレビュー回数の制限に当たった旨の報告を受けたら、解除時刻をその PR のハンドオフファイルに記録し、経過したら再レビュー依頼を子へ指示する。子には自分で待たせない。空いた枠を誰へ与えるかは HQ が決めるためである。

- 解除時刻の計算は `pr-review-loop` の解除時刻を出すスクリプトに任せ、表示された時間を自分で足さない
  - `BASIS=default` は分数を読めず、既定の 60 分で出した解除時刻である。記録には解除時刻が不明であることも書く
- 解除時刻まで `ScheduleWakeup` で待つときは、1 回の待ちを 3300 秒までにする
  - 起床は頼んだ時刻より遅れることがあり、3600 秒ではプロンプトキャッシュの有効期限（1 時間）を過ぎて起きうるため
  - 制限メッセージは制限に当たるたびに上書きされるため、その都度計算し直す
- 解除時刻を過ぎたら、その PR の子へ再レビュー依頼を送るよう指示する
- 指示した子が再び制限に当たったら、同じ手順で待ち直す
- 待つ間に、より優先すべき PR の申請が来たときだけ枠を配り直す
  - Ready の PR を draft へ戻すよう担当の子へ指示してから、次の PR へ許可を出す

## 稼働中の子への通知

進行中の子が前提にしていたものが動いたら、報告を待たずに自分から知らせる。先行 PR の main へのマージ、設計判断の変更、他タスクとの競合が該当する。

- 子が出した PR のマージを監視で検知したら、担当の子へ伝える（[LEDGER.md](LEDGER.md)）
  - 子はマージを自分で確認するまで完了報告を出さないため、HQ 止まりだと作業が終わらない
  - ユーザーから先にマージしたと聞いたときも同じく伝え、台帳の 🔀 を片付ける
  - 併せて Ready の枠が空くので、次に通す PR を決めて許可を送る
- 影響がある子だけに、1 通ずつ送る
  - 複数宛先への同時送信はできない
- 送るのは事実と依頼だけにし、取り込み方は子に委ねる
- 同じ内容を短時間に送り直さない
  - 重複は落とされる
- 発行済みのハンドオフの中身が変わったときは、ファイルを更新したうえで送る
  - 読み終えた子にはファイルの変更が届かない

## メッセージングが使えないとき

自分が受信できないとき、または子から届かないときは、コピペ方式に戻す。

- 子は確認・完了報告をコードブロックで出力し、人が HQ へ貼る
- HQ の返答もコードブロックで囲んで出力する
- 稼働中の子への通知もコードブロックで出力し、人が対象の子セッションへ貼る

## Don't

- タスクを sub-issue に分割しない
  - 残タスク issue で管理するときは、要件規模に関わらず 1 本に積む
- 残タスク issue を確認なく起票しない
  - 既存 issue の open / close で足りることがある
- タスクの遂行を自身で抱えない
  - 実装・レビューの機械作業は子セッションへ渡す
  - `Agent` ツールで肩代わりしない
  - ハンドオフを発行した後に手が空いても、自分で着手しない
- 子の Ready 化の申請を放置しない
  - 許可か見送りかを返すまで、子は draft のまま止まる
- Ready の PR を同時に 2 本以上にしない
  - レビュー枠を取り合い、割り込むと先行 PR のレビューが止まる
- ハンドオフの本文をチャットへ出さない
  - 人へ渡すのは、見出しと推奨モデルの行、タイトル・パス・HQ のセッション名の 3 行だけとする
- CHILD_BRIEFING.md への参照を、ハンドオフファイルの外に書かない
  - 子が読むのはファイルだけである
- HQ のセッション名をハンドオフファイルへ書かない
  - HQ 自身が別のセッションへ引き継がれると、本文の宛先は引き継ぎ前の HQ を指したまま残る
  - 宛先は、渡す時点の名前を人へ渡す 3 行目に入れて渡す
- ハンドオフの生成結果を先に確定させてから、後付けで足そうとしない
  - args で最初から含めるよう指定し、生成物自体を完成形にする
- 子から頼まれた操作を代行しない
  - 子の権限で拒否された操作を肩代わりすると権限の迂回になる
  - PR のマージ等はユーザーへ返し、子が人に頼む操作は 🙋 で取り次ぐ
- 子の完了報告に、了解した旨の返信を送らない
  - issue のチェックボックスを更新する
  - 進捗率を報告する
  - 次のタスクがある場合は、次のハンドオフを発行する
- 完了したハンドオフを保管先に残さない
  - 生きているものだけを置く。溜めると発行のたびに読む量が増える
  - セッションが閉じられたのを検知したら、すぐ片付ける
- 子の報告の詳細を、受けた時点でチャットへ出さない
  - R の番号と見出しだけを出し、詳細は台帳に置く
- 台帳のファイルを手で書き換えない
  - `scripts/ledger.sh` を通す。番号の採番と状態の書き換えを 1 か所に寄せるため
- 共有ツリーで状態を確認するときに、作業ファイルを書き換えるコマンドを使わない
  - 読み取りは `git show` / `git grep` で行う
  - `git checkout origin/main -- .` のようなコマンドは HEAD を動かさないまま作業ツリーとインデックスだけを書き換え、他セッションがそこに置いていた未コミットの変更を復元不能に失う
