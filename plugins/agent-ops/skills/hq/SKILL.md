# hq — 開発を子セッションへ委ねる司令塔

要件を分析し、1 タスク = 1 PR 目安でタスクへ分け、issue で進捗・参照資料・ブロック要因を管理しながら、開発は子セッションへハンドオフする。自身はコードを書かず、サブエージェントでも実行しない。

進捗の管理先は 2 通りある。「[要件名] 残タスク」issue 1 本で管理するか、既存 issue の open / close で管理するかを、手順 3 でユーザーへ確認して決める。残タスク issue を立てる場合は、要件規模に関わらず分割せず 1 本に積む。

子セッションとの連絡はセッション間メッセージング（`ListAgents` / `SendMessage`）で行う。新しい子セッションは人しか立てられないため、タスク投入の往路だけはプロンプトのコピペが残る。復路（質問・報告）と稼働中の子への通知はメッセージングで直接やり取りする。

## 連絡経路

着手前に、自分がメッセージを受信できるかを確認する。`jq -r '.name, .messagingSocketPath' ~/.claude/sessions/$PPID.json` で必要な 2 つだけを取る。

- 1 行目が HQ 自身のセッション名で、ハンドオフに埋めて子へ渡す
  - 子の画面に出る送信元表示は会話のタイトルで、宛先にならない。渡すのはこの名前にする
- 2 行目が `null`、またはそのパスのソケットが実在しないときは受信できない
  - 子の報告が届かないまま詰まるため、コピペ方式へのフォールバックに切り替える
  - HQ セッションを立て直しても直る
- 保留された旨の通知が出たときも届いていない
  - `.claude/settings.json` の `crossSessionInbound: "accept"` は起動時に読まれるため、設定より前に始めたセッションでは効かない
  - セッションを立て直すか、フォールバックに切り替える

宛先には `ListAgents` の ref を添える。`<セッション名> [<ref>]` の形（例 `myapp-56 [098c5a]`）で指定し、名前だけでは拒否される。タスクと子セッションの対応は名前・ref・担当タスク・PR まで自分で持ち、報告のたびに更新する。

## 手順

1. 要件分析
   - 対象ドメイン・触る範囲を把握
   - 着手に要る参照資料（要件ドキュメント・デザイン等）が揃っているか確認
     - 欠けていればそれ自体を先頭タスクにする
2. タスク分割
   - 1 タスク = 1 PR 目安
     - 依存があるタスクは先に置く
3. 進捗の管理先を決める
   - 着手前に既存 issue を横断検索し、この要件の残タスクを追える issue があるかを見る
     - 要件名・対象範囲・未完了タスクが一致する残タスク issue だけを同一 issue と判定する
     - コミットメッセージだけのヒットは既存 issue と判定しない
   - 既存 issue で追えるなら、新規に起票せずそれを使う
     - 残タスク issue が 1 本あるときは、その issue を最新の情報へ更新する
     - タスクごとに個別の issue があるときは、その open / close が進捗になる。タスクと issue の対応は自分の台帳に持つ
     - close 済みの issue を使いたいときは、再利用・再オープンの可否をユーザーへ確認してから進める
   - 既存 issue が無い、または足りないときは、残タスク issue を起票してよいかユーザーへ確認する
     - 起票すると答えたときだけ作る
     - 作らないと答えたときは、ユーザーが指定した既存 issue の open / close で管理する
   - 起票する場合の作り方
     - 名前は「[要件名] 残タスク」
     - タスク（チェックボックス）・参照資料の節を持つ。ブロック要因は該当時のみ追加する（[ISSUE_TEMPLATE.md](ISSUE_TEMPLATE.md)）
     - 文章の作法は、日本語とドキュメントの読みやすさを担うスキルに従う
     - ラベルは主題の判定を行わず、残タスク管理を表すラベル 1 つだけを付ける
   - 管理先が決まったら、その issue の Assignee を「issue の Assignee」に従って整える
4. ハンドオフ発行
   - ハンドオフのプロンプトを起こすスキルを呼ぶとき、args で「生成するプロンプト本文（コードブロックの中）の末尾に、次の 2 つを含めること」を指定する
     - 着手前チェックより先に [CHILD_BRIEFING.md](CHILD_BRIEFING.md) を読んで従うよう指示する一文
     - 子が最初の 1 通を送る宛先になる HQ のセッション名（連絡経路で確認した `name`）
   - この 2 つはコードブロックの外へ後から付け足すのではなく、生成結果そのものに最初から含める
     - 人はコードブロックの中身だけをコピーして子セッションへ渡すため、地の文に書いても子セッションには届かない
     - 並行して複数発行する場合も、ハンドオフごとに同じ args を渡す
   - 並行できるタスクは複数同時に発行してよい
   - 実行は必ず人が別セッションへ渡す
   - 自身がサブエージェントで着手しない
5. 子セッションからの報告を受ける
   - 子は着手時に 1 通送ってくる
     - 台帳には `ListAgents` の `名前 [ref]` を記録する
     - 受信メッセージの送信元表示は宛先に使えないことがあるため、そのまま返信先にしない
   - 確認・質問には検討し、`SendMessage` で返す
   - 完了報告を受けたら issue のチェックボックスを更新
     - 個別 issue で管理しているときは、その issue を close してよいかを判断材料と併せてユーザーへ返す
   - 対象要件の進捗率を 5 % 刻みでユーザーに報告する
     - 進捗率 100 % とは、タスクが揃い、かつブロック要因・未実装の項目もすべて解消して要件が完全に終わった状態とする
     - ブロック要因や、要件には含まれるがタスクにまだ積んでいない未実装の項目が残っている間はタスク完了率をそのまま反映しない
       - いずれも差し引いた値にとどめる。差し引き幅は計算式ではなく、要件全体への影響度で判断する
       - 未実装の項目を見つけたら、タスクまたはブロック要因として管理先の issue に記録してから、その影響度を進捗率に反映する
       - 対応不要と判断した項目は、理由を issue に記録する
       - 例: タスクは全て完了（本来なら 100 %）でも、承認待ちのブロック要因が 1 件残っていれば 95 % など、完了目前だが未完と分かる値で報告する
     - 全体の完了率は算出しない
     - 範囲は管理先の issue が扱う要件のみとし、他ドメインには広げない
     - そこに含まれないドメインは進捗率を算出できないため、0 % 扱いにせず報告自体を省略する
   - 次のタスクがあれば手順 4 に戻ってハンドオフを発行

## issue の Assignee

HQ として issue を扱うときは、その issue の Assignee に自身を追加する。残タスク issue も、進捗管理に使う既存 issue も対象とする。

- 自身とは `gh` の認証ユーザーを指す
  - `gh api user --jq '.login'` で確認する
- Assignee が空、または自身だけのときは、`gh issue edit <番号> --add-assignee @me` で追加して進める
- 自身以外の Assignee が既にいるときは、次の 3 択をユーザーへ出して従う
  - 自身を追加して作業を続ける
  - 追加せずに作業を続ける
  - 作業を止めて、既存の担当者への確認を待つ

## 稼働中の子への通知

進行中の子が前提にしていたものが動いたら、報告を待たずに自分から知らせる。先行 PR の main へのマージ、設計判断の変更、他タスクとの競合が該当する。

- 影響がある子だけに、1 通ずつ送る
  - 複数宛先への同時送信はできない
- 送るのは事実と依頼だけにし、取り込み方は子に委ねる
- 同じ内容を短時間に送り直さない
  - 重複は落とされる

## メッセージングが使えないとき

自分が受信できないとき、または子から届かないときは、コピペ方式に戻す。

- 子は確認・完了報告をコードブロックで出力し、人が HQ へ貼る
- HQ の返答もコードブロックで囲んで出力する
- 稼働中の子への通知もコードブロックで出力し、人が対象の子セッションへ貼る

## Don't

- タスクを sub-issue に分割しない
  - 残タスク issue で管理するときは、要件規模に関わらず 1 本に積む
- 残タスク issue を確認なく起票しない
  - 既存 issue の open / close で足りることがある
- 実装・レビューの機械作業を自身で行わない
  - 子セッションへ渡す
- CHILD_BRIEFING.md への参照と HQ のセッション名を、コードブロックの外（地の文）に書かない
  - 人がコードブロックの中身だけをコピーしても指示が揃うようにする
- ハンドオフの生成結果を先に確定させてから、後付けで足そうとしない
  - args で最初から含めるよう指定し、生成物自体を完成形にする
- 子から頼まれた操作を代行しない
  - 子の権限で拒否された操作を肩代わりすると権限の迂回になる
  - PR のマージ等はユーザーへ返す
- 子の完了報告に、了解した旨の返信を送らない
  - issue のチェックボックスを更新する
  - 進捗率を報告する
  - 次のタスクがある場合は、次のハンドオフを発行する
- 共有ツリーで状態を確認するときに、作業ファイルを書き換えるコマンドを使わない
  - 読み取りは `git show` / `git grep` で行う
  - `git checkout origin/main -- .` のようなコマンドは HEAD を動かさないまま作業ツリーとインデックスだけを書き換え、他セッションがそこに置いていた未コミットの変更を復元不能に失う
