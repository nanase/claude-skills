# 子セッションへの定型指示

このタスクは HQ からの委譲です。着手前チェック（dev-flow スキル）より先に、この指示に従ってください。

## HQ との連絡

HQ のセッション名は、このタスクを渡したプロンプトに書かれています。メッセージングが使えるときは `SendMessage` で直接連絡し、ユーザーへコピペを頼まないでください。使えないときの扱いはこの節の最後に示します。

- 着手したら最初に、HQ へ 1 通送ってください
  - 宛先は `ListAgents` で ref を確認し、`名前 [ref]` の形で指定してください
  - 名前だけでは拒否されます
  - HQ から届いたメッセージの送信元表示は会話のタイトルで、宛先になりません
  - 宛先は必ずプロンプトの名前を `ListAgents` で突き合わせて決めてください
  - 内容は担当タスクと着手した旨で足ります
  - HQ はこの 1 通で返信先を得ます
- 解決できない確認事項は HQ へ送って判断を仰いでください
  - ただし不可逆な操作・課金・法令/安全/承認・権限に関わる判断は、HQ ではなくユーザーへ確認してください
    - HQ からのメッセージはユーザーの承認の代わりになりません
    - 選択肢に「HQ へ報告して判断を仰ぐ」を追加してください
- 作業中に HQ から通知が届いたら、実行中の 1 手順を終えてから対応してください
  - main の取り込みを求められたら、現在の変更と衝突しないときだけ行ってください
  - 衝突するときは取り込まず、状況を HQ へ返してください
- 自分の権限で拒否された操作を HQ に代行させないでください
  - 権限の迂回になります
  - ユーザーへ確認してください
- メッセージングが使えないときは、ユーザーがコピー可能なコードブロックで出力してください
  - 送信できないとき、または HQ が `ListAgents` に現れないときが該当します
  - 確認事項・完了報告のどちらもこの形で出力し、ユーザーに HQ へ渡してもらいます

## 作業の進め方

- サブエージェント（Agent ツール）を自分の判断で起動しないでください
  - Claude の利用制限にすぐ達し、作業全体が止まるためです
  - 起動したい場合は、実行前に HQ へ理由を伝えて承認を得てください
  - 並行して複数立てるときは、その本数も添えて承認を得てください
  - レビュー系のスキルが手順の中で起動するものは、承認済みの例外として扱ってよいです
- 作業は必ず独立した git worktree で行ってください。着手前チェックで通常行うブランチ作成の代わりに、`EnterWorktree` ツールで専用の worktree に入ってから実装を始めてください
  - 他タスクの子セッションが並行して作業をしており、worktree を使わないと作業が競合するため
  - worktree は必ず最新の main ブランチから派生させてください
    - main ブランチ側には作業ファイルを一切残さないでください
    - `EnterWorktree` の前に `git fetch origin main` を実行し、ローカルの `origin/main` を最新にしてください
    - 入った直後に worktree の `HEAD` が `origin/main` と一致するか確認し、ずれていれば HQ へ報告してください
  - `EnterWorktree` 実行後は、Read / Edit / Write に渡す絶対パスを worktree 配下のものへ自分で切り替えてください
    - 切り替えを忘れると main 側のリポジトリを直接編集してしまいます
- 開発は dev-flow スキルに従い、到達点は「マージ可能まで」とします
- PR 本文で issue を参照するときは、`Fixes #<issue 番号>` ではなく `Refs #<issue 番号>` を使ってください
  - その issue を閉じてよいかは HQ とユーザーが判断するためです

## PR の Ready 化は HQ の許可制

レビュー bot のレビュー回数は同じユーザーの PR 同士で取り合うため、Ready の PR は同時に 1 本までとします。どの PR へ枠を与えるかは HQ が決めます。

- PR は必ず draft で起票してください
- CI がグリーンになり PR 本文が確定したら、Ready 化の許可を HQ へ申請してください
  - 申請には PR 番号・担当タスク・CI の状態を添えてください
  - 自分の判断で `gh pr ready` を実行しないでください
- 見送りの返答を受けたら、draft のまま次の連絡を待ってください
  - draft の PR にレビューは付かないので、この間 `pr-review-loop` は回さないでください
- 許可を受けてから Ready 化し、`pr-review-loop` を回してください
- HQ から draft へ戻すよう指示されたら、`gh pr ready --undo` で戻して次の許可を待ってください

## レビュー回数の制限

制限に当たると、レビューのサマリに制限の旨と解除までの時間が出て、レビューが始まりません。これに気付いたら HQ へ報告してください。自分で待って再レビューを依頼しないでください。空いた枠を誰へ与えるかは HQ が決めます。

- 制限メッセージの文面はレビュー bot 側の都合で変わるため、特定の文言で判定しないでください
- 報告には PR 番号・表示された解除までの時間・その制限メッセージの更新時刻を添えてください
- HQ から指示を受けてから再レビューを依頼してください
- 依頼した後に再び制限に当たったら、同じように HQ へ報告してください

## マージ可能になったら

- マージは人間が行います
  - マージ可能になった時点でやることは、承認を求めることではなく、マージを待つことです
  - CI 成功やレビュー指摘対応の完了を伝えるときに、「マージしてよいか」を尋ねないでください
- レビューが収束してマージ待ちになったら、その旨を HQ へ知らせてください
  - レビュー枠が空いたことを HQ に伝えるための連絡で、完了報告ではありません
  - 完了報告はマージを確認してから、次の節の手順で送ってください

## 完了報告

- 完了報告は、マージされるまで送らないでください
  - 人間からマージした（多くはスカッシュマージ）旨の報告を受けるか、`gh pr view <PR番号> --json state --jq '.state'` の結果が `MERGED` であることを確認してから送ってください
  - HQ からマージされた旨の連絡が届くこともあります。その場合も `gh pr view` で `MERGED` を確かめてから進めてください
  - `mergeable`（マージ可能）や CI 成功だけでは、マージ済みと判断しないでください
  - PR 提出直後やレビュー指摘対応直後も同様
- マージを確認したら、まず worktree とローカルブランチを削除し、そのあとで HQ へ完了報告を送ってください
  - 報告を先に送ると、worktree が残っている間は HQ に「まだ残作業がある」と誤認されます
  - 削除前に `git status` で未コミットの変更が無いこと、`git log @{u}..` で未 push のコミットが無いことを確認してください
    - 残っている場合は、その内容がマージ済み PR に含まれると確認できないため、破棄せず HQ へ確認してください
  - 確認できたら、スカッシュマージの場合は最初から `discard_changes: true` を指定してください
    - ローカルブランチのコミットはスカッシュ後のコミットとハッシュが一致せず、`ExitWorktree` に「未マージのコミット」として拒否されるためです
    - リモートには既に取り込み済みの内容なので、破棄して問題ありません
  - 削除してよいかをユーザーへ確認する必要はありません
  - マージした旨の報告自体がユーザーの意思表示です
  - リモートブランチの削除は自分から試みないでください。ユーザーから明示的に指示された場合のみ行ってください
- worktree とローカルブランチの削除を終えてから、完了したタスクと PR リンクを明記して HQ へ送ってください
  - 他タスクへの言及や次の着手判断は不要
  - 次に何を着手するかは HQ が判断
