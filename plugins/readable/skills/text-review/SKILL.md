# text-review — 文言の判定をまとめて人に渡す

文言を直す前に、対象と修正案を 1 枚のページへ並べて公開し、人に判定させる。判定を受け取り、反映するところまでを担う。

画面の文言でも文書の用語でも同じく使う。短い文字列が大量にあり、1 件ずつ会話でやりとりすると手間がかかる状況に効く。

文言の当否は好みと文脈で決まるため、test も AI レビューも判定できない。だから案が揃った時点で人へ渡す。

## 発動するか — 判定させる文言が 5 件以上あるときだけ

件数と、判定の余地があるかで決める。

- 判定させる文言が 5 件以上ある → 発動する
- 4 件以下 → 発動しない
  - 会話で聞くほうが速い
- 誤字・表記ゆれの機械的な統一 → 発動しない
  - 直して差分で見せる
  - 確認したい語が混ざるなら、その語だけ並べる
- 迷ったら発動する

## 1 件の切り方

表示される 1 つの文字列を 1 件とする。同じ文言が複数の箇所に出るなら 1 件にまとめ、使用状況に全ての箇所を書く。別々に判定させると片方だけ直り、文言が揺れる。

各件に次の 4 つを持たせる。

| 項目 | 中身 |
| --- | --- |
| 区分 | 画面名・章名。この単位でページが区切られる |
| 種別 | ボタン・見出し・用語など |
| 対象の文言 | 元のまま正確に写す |
| 使用状況 | 判定に必要なことだけを 1〜2 文で書く |

使用状況に書くのは、どこに出るか・押すと何が起きるか・誰が読むかである。実装の都合は書かない。

## 修正案の作り方

- 案は 1 つに絞る
  - 複数案から選ばせる方法は別の仕組みが担う
- 直す必要がないものには案を作らない
  - 埋めるために案を作らない
- 理由を添えない
  - 判定は案そのものを見て下される

## 公開する

1. [TEMPLATE.html](TEMPLATE.html) を作業用の場所へ写す
2. `<title>`・`REVIEW`・`ITEMS` の 3 か所だけ書き換える
   - 他は触らない
3. Artifact ツールで公開する
   - `capabilities: {db: {}}` を必ず付ける
   - 付け忘れると判定が保存されず、結果も読めない
4. URL を添えて判定を頼む

1 回の公開は 100 件までとする。超えるなら区分で分け、回を分ける。

同じ検討は同じファイルパスへ書き直して再公開する。パスを変えると別の URL になり、貼ったリンクが古い版を指したままになる。アイコンは最初の公開でだけ指定する。

## 判定を受け取る

人が終わったと言うまで読まない。途中の状態を確定として扱わない。

Artifact ツールの `read_db` で読む。まず `session` の `state` を読んで `done` を確かめ、次に `decisions` を list する。id ごとに次が入る。

| status | 意味 | 反映 |
| --- | --- | --- |
| `kept` | 修正なし | 触らない |
| `adopted` | 修正案を採用 | 案へ書き換える |
| `edited` | 人が書き直した | `text` の文言へ書き換える |
| `held` | 保留 | `note` を読んで次の回へ回す |

`decisions` に無い id は判定されていない。完了扱いにせず、人に確かめる。

## 反映する

書き換えた結果は差分で見せてから当てる。同じ文言が複数の箇所にあるなら全部直す。

## 保留を次の回へ回す

保留の `note` を読んで案を作り直し、保留分だけに絞って同じファイルパスへ再公開する。判定済みを残すと、また上から流すことになる。

再公開の前に、保留にした id の判定を `write_db` で消す。残っていると保留のまま復元され、その場で判定できなくなる。

## 外へ出す前に確かめる

ページは既定で非公開だが、手元から出て claude.ai 上に置かれる。未公開の機能名・顧客の文言を載せるときは、出してよいかを先に確かめる。
